# Question 8: Data Leakage in Churn Prediction

**Topics:** Data Leakage, Snapshots, Model Evaluation, Churn Prediction

## 📝 Question

> A user asked an AI assistant to evaluate a customer churn prediction model. The assistant's answer: “I extracted the data from the current snapshot of the users table (40 thousand users). The features were average monthly purchase, number of support contacts, number of app logins in the last 30 days, and ‘days remaining until the end of the subscription’. I split the data randomly 80/20, and an XGBoost model reached an AUC of 0.96 on the test set. Given this high number and the absence of overfitting (training AUC 0.97), the model is ready for deployment.” What is the main problem with this analysis?

## 🔢 Options

**Option 1:** The closeness of the training and test AUC proves there is no information leakage; the only problem is the small number of features.

**Option 2:** An AUC of 0.96 is unrealistic for churn problems, and for that reason alone the whole evaluation should be rejected.

**Option 3:** XGBoost is not suitable for tabular data, and a deep neural network should replace it for the result to be valid.

**Option 4:** The features were built from the current snapshot; for example, ‘days remaining’ has changed for users who cancelled after cancellation and leaks the label, so the high number cannot be relied upon.

## 💡 About this question

This question tests **data leakage**: when features contain information from **the future or from the label itself** that would not be available at real prediction time.

The key detail: the data was taken from the "current snapshot." For a user who cancelled the subscription, values such as "days remaining until the end of the subscription" (and even "app logins in the last 30 days") change after cancellation and take on distinctive patterns; so the model is effectively reading the *outcome* from the features.

An important point: **similar training and test AUC does not prove there is no leakage**, because the leakage is present equally in both parts (which were split randomly).

## 🔍 Detailed review of every option

### Option 1 — ❌ Incorrect

> The closeness of the training and test AUC proves there is no information leakage; the only problem is the small number of features.

**Incorrect.** Similar training and test AUC only shows there is no classic overfitting, not that there is no leakage. The leakage is equally present in both parts, since both come from the same snapshot with a random split. The claim that "the only problem is the small number of features" is also unfounded.

### Option 2 — ❌ Incorrect

> An AUC of 0.96 is unrealistic for churn problems, and for that reason alone the whole evaluation should be rejected.

**Incorrect.** A high AUC alone is not a reason to reject an evaluation; depending on the problem the model may truly be good. 0.96 can be a **warning sign** to check for leakage, but the reason to reject the evaluation is the *specific cause*: the features leaking from the snapshot.

### Option 3 — ❌ Incorrect

> XGBoost is not suitable for tabular data, and a deep neural network should replace it for the result to be valid.

**Incorrect.** XGBoost and tree-based models are usually among the best choices for tabular data and are often better than or on par with deep networks. Replacing the model does not solve leakage; any model gives optimistic results on leaky features.

### Option 4 — ✅ Correct

> The features were built from the current snapshot; for example, ‘days remaining’ has changed for users who cancelled after cancellation and leaks the label, so the high number cannot be relied upon.

**Correct.** The features were built from the "current" state and, for users who cancelled, changed after cancellation; so they reveal the label (churn). The right approach is to build features from a snapshot at a **cutoff date** before churn occurs, take the label from the period after it, and split by time. Until then, 0.96 cannot be trusted.

## ✅ Correct answer

**Option 4**

> The features were built from the current snapshot; for example, ‘days remaining’ has changed for users who cancelled after cancellation and leaks the label, so the high number cannot be relied upon.

## 🎯 Why it is correct

The core problem is building features from data that was updated **after the label event** (the current snapshot). That is leakage from the future; a high AUC and no overfitting hide this problem rather than resolve it.

## 📌 Key takeaway

Features must be built only from information that exists at prediction time. For time-dependent data use a cutoff date and a time-based split.
