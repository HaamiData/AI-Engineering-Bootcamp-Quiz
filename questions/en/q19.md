# Question 19: Learning Strategy for a New Tool Under Time Pressure

**Topics:** Hands-on Learning, Documentation, Working with AI Assistants, Time Management

## 📝 Question

> Your team has chosen a new data-versioning tool for next week's project that you have never worked with before. Its documentation is 300 pages and time is limited. Which learning strategy is more effective?

## 🔢 Options

**Option 1:** Ran a small example with the quick-start guide, then whenever a capability was needed read that part of the documentation and tested the result.

**Option 2:** Asked the AI assistant to write all the steps and applied them directly in the main project without a trial run.

**Option 3:** Read all 300 pages of documentation in order before touching the tool so that no detail is missed.

**Option 4:** Waited for an experienced teammate to teach the whole tool and did nothing until then.

## 💡 About this question

This question tests an **engineering learning strategy**: when time is limited and documentation is large, effective learning is **targeted, hands-on and feedback-driven**. Get a small, testable result quickly, then go deeper as needed.

## 🔍 Detailed review of every option

### Option 1 — ✅ Correct

> Ran a small example with the quick-start guide, then whenever a capability was needed read that part of the documentation and tested the result.

**Correct.** Running a small example from the quick-start guide is the fastest way to build a "mental model." Then, as real needs arise (just-in-time), the relevant documentation section is read and the result is tested immediately; a short read → run → feedback loop. This approach is fast and exposes mistakes in a safe environment.

### Option 2 — ❌ Incorrect

> Asked the AI assistant to write all the steps and applied them directly in the main project without a trial run.

**Incorrect.** Using an AI assistant is good, but running its instructions directly in the main project without trying them is risky: the assistant may be wrong or incompatible with the tool's version, and the project's data (especially in a data-versioning tool) could be damaged. Every step should first be verified in a sandbox.

### Option 3 — ❌ Incorrect

> Read all 300 pages of documentation in order before touching the tool so that no detail is missed.

**Incorrect.** Reading 300 pages in order before starting is impractical under time pressure, and a large part of it is irrelevant to this project's needs. Without practice, much of it also won't stick. Learning should be paired with doing.

### Option 4 — ❌ Incorrect

> Waited for an experienced teammate to teach the whole tool and did nothing until then.

**Incorrect.** Passive waiting wastes time and endangers next week's project. The teammate may be unavailable, and teaching "the whole tool" isn't necessary. Asking a teammate questions is helpful, but it shouldn't replace active effort to learn.

## ✅ Correct answer

**Option 1**

> Ran a small example with the quick-start guide, then whenever a capability was needed read that part of the documentation and tested the result.

## 🎯 Why it is correct

The shortest path to usable skill: a small example + on-demand reading of the docs + immediate testing. The other options are either risky, slow or passive.

## 📌 Key takeaway

For a new tool: quick start and a small example first, then targeted reading and testing; try anything an assistant or doc says before using it on the main project.
