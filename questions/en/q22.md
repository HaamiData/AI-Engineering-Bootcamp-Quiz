# Question 22: Query Rewriting in Conversational RAG

**Topics:** Conversational RAG, Query Rewriting, Coreference to Earlier Messages, Retrieval

## 📝 Question

> In a chat, a user asks ‘How much does it cost?’ (referring to the product in the previous message) and RAG returns irrelevant results. Why, and what is the solution?

## 🔢 Options

**Option 1:** The embedding model is broken and should be discarded, relying only on keyword search.

**Option 2:** The query on its own is ambiguous; before retrieval it should be rewritten, with the help of the conversation history, into a standalone, complete query.

**Option 3:** The user must be required to write every query completely, without referring to previous messages, so that retrieval works correctly.

**Option 4:** Top-K should be made very large so that the relevant document is guaranteed to be among the results even with an ambiguous query.

## 💡 About this question

In conversation, users refer back to earlier messages ("how much is it?", "what about that one?"). The retriever sees **only that single sentence**, and "it" without knowing "what" is meaningless; so it returns irrelevant results.

The common solution: **query rewriting (condense-question)**; using the history, turn the query into a standalone, complete one (for example "How much does the camera model X cost?") and retrieve with it.

## 🔍 Detailed review of every option

### Option 1 — ❌ Incorrect

> The embedding model is broken and should be discarded, relying only on keyword search.

**Incorrect.** The problem is not the embedding; it is the **ambiguous input**. Any embedding model, and even keyword search, would perform poorly with "how much does it cost?" because the query lacks information. Discarding embeddings does not solve it and also loses semantic ability.

### Option 2 — ✅ Correct

> The query on its own is ambiguous; before retrieval it should be rewritten, with the help of the conversation history, into a standalone, complete query.

**Correct.** The query alone is ambiguous. Rewriting it with the conversation history (for example with a small LLM call) into a standalone query gives the retriever a clear input. This pattern is standard in conversational RAG systems.

### Option 3 — ❌ Incorrect

> The user must be required to write every query completely, without referring to previous messages, so that retrieval works correctly.

**Incorrect.** Forcing the user hurts the user experience and goes against the nature of natural conversation. Understanding the context is the system's job, not the user's.

### Option 4 — ❌ Incorrect

> Top-K should be made very large so that the relevant document is guaranteed to be among the results even with an ambiguous query.

**Incorrect.** A very large Top-K means more noise, cost and latency, and it gives no "guarantee." An ambiguous query has an ambiguous vector, and the right document may not be in the results at all. The root fix is to clarify the query.

## ✅ Correct answer

**Option 2**

> The query on its own is ambiguous; before retrieval it should be rewritten, with the help of the conversation history, into a standalone, complete query.

## 🎯 Why it is correct

The root problem is query ambiguity, and the principled fix is to remove the ambiguity before retrieval (rewriting with history).

## 📌 Key takeaway

In conversational RAG, convert the query into a standalone one using the history before retrieval.
