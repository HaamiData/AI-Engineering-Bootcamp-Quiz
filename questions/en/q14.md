# Question 14: Tuning Hyperparameters on the Test Set

**Topics:** Test Set, Validation Set, Leakage, Unbiased Evaluation

## 📝 Question

> A team changed hyperparameters 50 times, evaluating the model on the test set each time, and then reports the best result. What is the problem?

## 🔢 Options

**Option 1:** Reporting the best result is fine, because the final goal is to find the best possible performance of the model, and the test set does exactly that.

**Option 2:** The settings should have been compared on the training data, because the test set is only for comparing different model architectures.

**Option 3:** 50 experiments are not enough to find a suitable setting, and for a reliable report it should be repeated at least a few hundred times.

**Option 4:** By choosing the best of 50 evaluations on the test set, that set has effectively taken part in the tuning process, and the reported number is optimistic.

## 💡 About this question

The test set gives an **unbiased** estimate of performance on new data only when **no decision** is made based on it. If we evaluate 50 configurations on it and pick the best, we have effectively "selected" using the test set, and that set has taken part in the tuning process (like a validation set).

As a result, part of the high score comes from "luck and fitting this set's noise," and the reported number becomes optimistic. The more experiments we run, the larger this bias.

## 🔍 Detailed review of every option

### Option 1 — ❌ Incorrect

> Reporting the best result is fine, because the final goal is to find the best possible performance of the model, and the test set does exactly that.

**Incorrect.** The test set's purpose is not to find the best *possible* performance; it is to give an honest estimate of real performance. If used as a search tool, it is no longer an unbiased measure and the reported number overstates real performance.

### Option 2 — ❌ Incorrect

> The settings should have been compared on the training data, because the test set is only for comparing different model architectures.

**Incorrect.** Comparing settings on the training data is misleading (more complex models always look better on training data, and overfitting goes unnoticed). And the claim that "the test set is only for comparing architectures" is also wrong; the test set is for final evaluation, not for selection. Selection should be done on a **validation set** or with cross-validation.

### Option 3 — ❌ Incorrect

> 50 experiments are not enough to find a suitable setting, and for a reliable report it should be repeated at least a few hundred times.

**Incorrect.** The number of experiments is not the main problem; repeating more on the same test set makes the optimistic bias **larger**. The problem is how the test set is used, not how many trials there are.

### Option 4 — ✅ Correct

> By choosing the best of 50 evaluations on the test set, that set has effectively taken part in the tuning process, and the reported number is optimistic.

**Correct.** Taking the best of 50 evaluations on the test set means selecting based on that set; so the test set is no longer "unseen" and the number is optimistic. The right way: tune on a validation set (or cross-validation / nested CV) and evaluate **once** on the test set at the end.

## ✅ Correct answer

**Option 4**

> By choosing the best of 50 evaluations on the test set, that set has effectively taken part in the tuning process, and the reported number is optimistic.

## 🎯 Why it is correct

Every time we make a decision based on test-set results, information from it leaks into the model/settings. Choosing the best of 50 amplifies this leakage and makes the report optimistic.

## 📌 Key takeaway

Respect the Train / Validation / Test split: tune on validation, report once on test.
