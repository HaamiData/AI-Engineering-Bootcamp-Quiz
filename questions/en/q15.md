# Question 15: Preventing Quality Regressions After a Prompt Change

**Topics:** Automated Evaluation, CI, Monitoring, LLMOps

## 📝 Question

> A small change to a prompt was deployed and response quality silently degraded for a week. Which practice would have prevented this?

## 🔢 Options

**Option 1:** Automatically running an evaluation suite in CI before every deployment, together with continuous monitoring of response quality in production.

**Option 2:** Relying on feedback from dissatisfied users, who will surely and quickly report directly to the team if quality drops.

**Option 3:** Having a teammate review the prompt change as text before deployment, without running any automated test on the outputs.

**Option 4:** Reducing deployment frequency to once a month so fewer changes reach production and the chance of quality degradation is lower.

## 💡 About this question

In LLM systems, a prompt is like **code**: a small change can alter behavior unexpectedly, and since the output is free text, quality degradation usually happens "silently" (no errors or exceptions).

The standard solution is the same software-engineering discipline: **automated testing before deployment** (an evaluation suite in CI) and **continuous monitoring in production**.

## 🔍 Detailed review of every option

### Option 1 — ✅ Correct

> Automatically running an evaluation suite in CI before every deployment, together with continuous monitoring of response quality in production.

**Correct.** An evaluation suite in CI before every deployment catches change-induced quality drops before they reach users; and continuous production monitoring quickly reveals cases the earlier tests did not cover (shifting input patterns, model or data changes). Together they both prevent incidents and shorten detection time.

### Option 2 — ❌ Incorrect

> Relying on feedback from dissatisfied users, who will surely and quickly report directly to the team if quality drops.

**Incorrect.** Most dissatisfied users do not report; they just leave, and feedback is late and sparse. Relying on user feedback means discovering the problem after damage is done. The claim that such feedback will "surely and quickly" arrive is unrealistic.

### Option 3 — ❌ Incorrect

> Having a teammate review the prompt change as text before deployment, without running any automated test on the outputs.

**Incorrect.** Textual review is valuable, but predicting a prompt change's effect on outputs by reading the text is hard; seemingly harmless edits can ruin quality. Without running tests on outputs, quality drops stay invisible.

### Option 4 — ❌ Incorrect

> Reducing deployment frequency to once a month so fewer changes reach production and the chance of quality degradation is lower.

**Incorrect.** Deploying less often makes each change bigger and riskier, and makes finding the cause harder. The core problem is the lack of tests and monitoring, not deployment frequency; every deployment, monthly or daily, carries the same risk without evaluation.

## ✅ Correct answer

**Option 1**

> Automatically running an evaluation suite in CI before every deployment, together with continuous monitoring of response quality in production.

## 🎯 Why it is correct

A "silent" drop is visible only through active measurement: automated evaluation before deployment and monitoring after it. The other options are late (user feedback), insufficient (textual review) or beside the point (fewer deployments).

## 📌 Key takeaway

Treat prompts like code: versioning, automated tests on an evaluation set in CI, and production monitoring.
