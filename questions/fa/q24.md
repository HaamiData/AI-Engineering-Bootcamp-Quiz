# سوال ۲۴: بازبینی روش ارزیابی طبقه‌بند اسپم

**موضوع‌ها:** داده نامتوازن، Precision/Recall/F1، نشت اطلاعات، Train/Validation/Test

## 📝 متن سوال

> تیمی از یک دستیار هوش مصنوعی خواست روش ارزیابی یک طبقه‌بند ایمیل اسپم را مرور کند. پاسخ دستیار: «۹۵٪ ایمیل‌ها غیراسپم‌اند، پس به‌جای Accuracy از Precision، Recall و F1 برای کلاس اسپم استفاده کردم. بردارساز TF-IDF را فقط روی داده آموزش Fit کردم و روی Validation و Test فقط Transform زدم. آستانه تصمیم را با Validation تنظیم کردم و مدل نهایی را فقط یک بار در انتها روی Test ارزیابی کردم. نتیجه: Precision برابر ۰٫۹۱ و Recall برابر ۰٫۸۷.» کدام گزینه درباره این پاسخ درست است؟

## 🔢 گزینه‌ها

**گزینه ۱:** آستانه باید روی Test تنظیم می‌شد تا بهترین Precision و Recall ممکن روی داده نهایی به دست آید

**گزینه ۲:** TF-IDF نباید فقط روی Train فیت شود و باید روی کل داده فیت شود تا واژگان Validation و Test هم پوشش داده شوند

**گزینه ۳:** Accuracy تنها معیار معتبر برای این مسئله است و باید به‌جای Precision و Recall گزارش شود

**گزینه ۴:** از نظر روش‌شناسی مشکل مشخصی دیده نمی‌شود؛ انتخاب معیارها، جلوگیری از نشت اطلاعات و استفاده یک‌باره از Test درست است

## 💡 توضیح سوال

این سوال برعکس چند سوال قبلی یک **تله‌ی معکوس** دارد: گاهی پاسخ دستیار از نظر روش‌شناسی درست است و باید جلوی «ایراد‌گیری الکی» ایستاد. چهار نکته‌ی روش‌شناسی را یکی‌یکی بررسی می‌کنیم:

1. **معیار:** داده نامتوازن است (۹۵٪ غیراسپم)؛ مدلی که همه را غیراسپم بداند ۹۵٪ Accuracy دارد. پس Precision/Recall/F1 برای کلاس اسپم انتخاب درستی است.
2. **TF-IDF:** باید فقط روی Train فیت شود و روی Validation/Test فقط Transform بخورد تا اطلاعات (واژگان و IDF) از داده‌ی ارزیابی نشت نکند.
3. **آستانه:** باید روی Validation تنظیم شود، نه Test.
4. **Test:** فقط یک‌بار در پایان استفاده شود.

هر چهار مورد در پاسخ دستیار رعایت شده است.

## 🔍 بررسی کامل هر گزینه

### گزینه ۱ — ❌ نادرست

> آستانه باید روی Test تنظیم می‌شد تا بهترین Precision و Recall ممکن روی داده نهایی به دست آید

**نادرست.** تنظیم آستانه روی Test یعنی انتخاب بر پایه‌ی Test Set و نشت اطلاعات؛ عدد نهایی خوش‌بینانه می‌شود. آستانه باید روی Validation تنظیم شود و Test فقط برای یک ارزیابی نهایی بماند، که دستیار دقیقاً همین را انجام داده است.

### گزینه ۲ — ❌ نادرست

> TF-IDF نباید فقط روی Train فیت شود و باید روی کل داده فیت شود تا واژگان Validation و Test هم پوشش داده شوند

**نادرست.** فیت کردن TF-IDF روی کل داده باعث می‌شود آماری از Validation و Test (واژگان و وزن‌های IDF) وارد مرحله‌ی آموزش شود، یعنی نشت اطلاعات. در استقرار واقعی هم ایمیل‌های آینده در زمان آموزش دیده نشده‌اند؛ واژه‌های ناآشنا طبیعی هستند و باید همین‌طور شبیه‌سازی شوند.

### گزینه ۳ — ❌ نادرست

> Accuracy تنها معیار معتبر برای این مسئله است و باید به‌جای Precision و Recall گزارش شود

**نادرست.** Accuracy در داده‌ی نامتوازن گمراه‌کننده است: دسته‌بندی که همه‌ی ایمیل‌ها را غیراسپم بداند ۹۵٪ Accuracy می‌گیرد ولی هیچ اسپمی را نمی‌گیرد. ادعای «تنها معیار معتبر» غلط است؛ Precision، Recall و F1 برای کلاس اقلیت مناسب‌ترند.

### گزینه ۴ — ✅ صحیح

> از نظر روش‌شناسی مشکل مشخصی دیده نمی‌شود؛ انتخاب معیارها، جلوگیری از نشت اطلاعات و استفاده یک‌باره از Test درست است

**درست.** انتخاب معیارها (Precision/Recall/F1 به دلیل عدم توازن)، جلوگیری از نشت (Fit فقط روی Train) و تنظیم آستانه روی Validation و استفاده‌ی یک‌باره از Test همگی درست‌اند. پس ایراد روش‌شناسی مشخصی دیده نمی‌شود.

## ✅ گزینه صحیح

**گزینه ۴**

> از نظر روش‌شناسی مشکل مشخصی دیده نمی‌شود؛ انتخاب معیارها، جلوگیری از نشت اطلاعات و استفاده یک‌باره از Test درست است

## 🎯 علت درست بودن

هر چهار تصمیم روش‌شناسی دستیار استاندارد و درست است. بقیه‌ی گزینه‌ها یا نشت ایجاد می‌کنند (۱ و ۲) یا معیار نامناسب پیشنهاد می‌دهند (۳).

## 📌 نکته کلیدی

الگوی استاندارد: معیار متناسب با عدم توازن، Fit پیش‌پردازش فقط روی Train، تنظیم هایپرپارامتر/آستانه روی Validation و ارزیابی نهایی یک‌بار روی Test.
